# Architecture: many teams sharing one AI platform

How ML teams share infrastructure safely. This is a **design**. Only the Kubernetes files and the application are in this repo; the VPC below is a validated plan, not a provisioned network.

## The decision: shared cluster, layered isolation

Teams share one EKS cluster per environment inside one VPC, isolated in layers. The alternative, an AWS account per team, gives stronger isolation (separate blast radius, separate bill) but multiplies cluster, networking and operations cost. Start shared; give a team its own account only when its data sensitivity or scale demands it, connecting accounts over PrivateLink or Transit Gateway.

First questions to ask before committing: how many teams, how much do they trust each other, is any data regulated, is GPU capacity scarce?

## Network layout

One VPC (`10.20.0.0/16`), three availability zones, three tiers. Generated by [infra/network/plan.py](../infra/network/plan.py) and checked by a test that fails on overlap, out-of-range subnets, a missing zone, or an app tier too small for pods.

| Tier | AZ | CIDR | Usable IPs |
|---|---|---|---|
| public | a | 10.20.0.0/24 | 251 |
| public | b | 10.20.1.0/24 | 251 |
| public | c | 10.20.2.0/24 | 251 |
| private-app | a | 10.20.32.0/20 | 4091 |
| private-app | b | 10.20.48.0/20 | 4091 |
| private-app | c | 10.20.64.0/20 | 4091 |
| private-data | a | 10.20.10.0/24 | 251 |
| private-data | b | 10.20.11.0/24 | 251 |
| private-data | c | 10.20.12.0/24 | 251 |

- **public**: load balancers and NAT gateways only. Nothing else lives here.
- **private-app**: EKS nodes and pods. It is a `/20` because the VPC CNI gives every pod a VPC IP address, so small subnets run out of addresses long before they run out of CPU.
- **private-data**: databases. No route to the internet at all.
- `10.20.128.0/17` is left free for growth, for example dedicated subnets for a team.

## Who may talk to whom

| From | To | Why |
|---|---|---|
| Internet | load balancer (443) | the only public entry |
| load balancer | platform API pods (8000) | security group references the load balancer's group, not an IP range |
| node and pod group | database (5432) | the database accepts only that group |
| private-app | AWS services via VPC endpoints | S3 (gateway endpoint, free), ECR, STS and CloudWatch Logs (interface endpoints): private traffic, less NAT cost |

Security groups are the main control (stateful, reference other groups). Network ACLs are only a coarse backstop. VPC Flow Logs go to a central bucket for audit.

## Isolation layers between teams

| Layer | Mechanism | What it stops |
|---|---|---|
| Account | Organizations, service control policies | one environment affecting another |
| Network | tiered subnets, security groups | internet or app reaching the database directly |
| Cluster | namespace per team, NetworkPolicy ([infra/k8s/network-policies.yaml](../infra/k8s/network-policies.yaml)) | a team's pods reaching another team's pods |
| Resources | ResourceQuota, LimitRange, job quota in the API | one team starving the others (noisy neighbour) |
| Identity | RBAC, IAM role per team (IRSA) | a team reading another team's data or S3 prefix |
| Data | per-team S3 prefixes and KMS keys, database roles | data crossing teams |
| Cost | team labels and tags | nobody paying for what they cannot see |

GPU nodes get their own node group with a taint, so only jobs that ask for a GPU land there.

## Failure and cost notes

- A NAT gateway per zone survives a zone loss but costs more; one shared NAT is cheaper and a single point of failure. Choose per environment.
- The platform API runs one replica until it uses PostgreSQL instead of SQLite.
- Quota is enforced twice (API admission and ResourceQuota), so a bug in one still leaves the other.

## Built vs designed

| Built and tested | Designed only |
|---|---|
| Per-team quota, team isolation, job manifests, registry, SLO rules | VPC, subnets, security groups, endpoints, flow logs |
| Namespace, ResourceQuota, NetworkPolicy, RBAC manifests (render only) | account structure, IRSA roles, KMS keys, GPU node group |
